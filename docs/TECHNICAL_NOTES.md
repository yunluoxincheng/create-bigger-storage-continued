# Vault implementation notes

Version 1.2.1 packages the completed vault-summary rebuilding, deferred-copy and scoped-NBT implementations, full-package source-scan optimization and manual diagnostics described here. Earlier references to development candidates and published 1.2.0 describe their historical verification scope; they do not add unperformed gameplay or net FPS/TPS acceptance to 1.2.1.

These notes describe inventory and structure behavior relevant to maintenance and automation. Version requirements and verification boundaries are maintained in [COMPATIBILITY.md](COMPATIBILITY.md).

## Inventory notifications and comparators

Since 1.1.2, real slot changes invalidate the current controller's comparator reading and queue notifications. A controller normally performs at most one structure-wide notification round per server tick; changes occurring during notification remain queued for a later round.

Comparator output uses Create's inventory redstone calculation and is shared across the structure until inventory, structure, NBT loading or capability changes invalidate it. Incomplete structures must not cache a temporary zero result.

Notifications may wait until the next controller tick, and intermediate changes within one tick are combined. Terminal inventory reads, writes and Create inventory-version updates remain immediate; the batching does not defer the inventory operation itself.

## Saving and client synchronization

- A changed member's chunk is marked for saving immediately through `blockEntityChanged`, avoiding the comparator work attached to `setChanged`. Repeated marks in a tick are combined; a mutation after a complete save/snapshot marks it again.
- Opaque vaults do not request client updates for inventory-only changes, and client structure/chunk data omits their inventories.
- Crystal vaults send only the first half of local slots used by the existing internal item renderer. Visible-slot changes are coalesced at the member tick; count, NBT and slot positions are retained. Changes to unused slots do not independently request rendering updates.
- Server persistence retains the complete inventory and storage type. Client render data is not a replacement for save data.
- NBT reads invalidate local caches and queue work without resolving other block entities just to notify them. Regrouping transfers pending notifications to the current controller.

Multiple vaults still tick, and external storage mods may build indexes or scan slots. These changes do not remove all possible sources of terminal or modpack latency; no measured FPS/TPS improvement is claimed here.

## Capability invalidation during chunk teardown

Client chunk replacement removes existing block entities while iterating their collection. Calling `Level.getBlockEntity` from an invalidation callback can delete a removed controller and recreate it, changing the collection during iteration. The resulting exception interrupts chunk/NBT replacement and can leave inconsistent client controller data used by connected textures. This path existed in 1.1.1 and the published 1.2.0.

The development fix invalidates client capabilities locally. On a real server, it reads the controller only from `getChunkNow` and the existing block-entity map, without creating entities or loading chunks; removed or mismatched controllers are skipped. Active server controller inventory, identifier and comparator caches still invalidate. Stored inventory, item NBT, notification batching and texture resources are unaffected. Initial user retesting reports no issue so far; updated logs and broader gameplay checks have not yet been reviewed. Published 1.2.0 artifacts remain unchanged.

## Combined inventory lookup

1.2.0 uses Create's `SameSizeCombinedInvWrapper.create` inside the existing versioned inventory wrapper. Equal-capacity members allow direct slot-to-member lookup; mixed capacities use the standard fallback. This does not change per-block inventory ownership, capacities or the upgrade transaction.

## Threshold-switch compatibility selection

The development optimization wraps only the compatibility-filter operation in Create's `ThresholdSwitchBlockEntity.updateCurrentLevel`. It selects the first matching storage adapter on the first scanned slot and reuses that selection for the rest of the same invocation. The no-match result is cached too. MixinExtras shared locals keep the selection separate for each invocation, including recursive calls; it does not persist across target changes or later scans.

Create still calculates each slot's capacity through the selected adapter, or its original fallback when none matches. Item filtering, empty slots, zero-capacity slots, inventory-version tracking, fluid scanning and redstone/display updates retain their upstream logic. This hook applies to item inventories observed by Create threshold switches, not only this mod's vaults. Full inventory scanning and per-slot Stream processing remain; packager summaries and vault notifications are separate optimization work. No measured FPS/TPS improvement is claimed.

The hook uses the existing MixinExtras 0.4.1 runtime supplied by the supported Create distributions and requires exactly one matching injection point. Both runtime JAR manifests register the Mixin configuration; development launches register it explicitly. The hook targets Create and Java Stream names only and does not require Minecraft name remapping.

Development compilation and Forge data-generation initialization passed with Create 6.0.6-150, 6.0.7-281 and 6.0.8-289. Exported transformed classes confirm the hook and invocation-local cache in each version; generated resources were unchanged. These checks do not establish packaged-client gameplay, optional-mod compatibility or measured performance gains.

Threshold-switch samples fell from 442/1738 server-thread samples (25.43%) to 193/1288 (14.98%); compatibility-selection samples fell from 113 to zero. ## Shared vault summaries for packagers

The initial shared-summary development candidate extends Create's `VersionedInventoryWrapper`, preserving its inventory identity and version tracking. Each combined vault handler owns separate extractable-item and input-slot snapshots. In that candidate, successful real mutations and controller notifications clear both snapshots. Capability reconstruction creates a new wrapper with empty caches. There is no global cache keyed by world positions, and the hook only handles this mod's combined vault inventories. The subsequent incremental implementation is described below.

The first query after invalidation scans the slots using Create's original slot-limit and simulated-extraction rules, or copies slot contents for input scanning. Item grouping still uses `InventorySummary.add` and its NBT/capability-sensitive comparisons. A version/revision check prevents retaining a scan invalidated by reentrant callbacks. Later queries for the same unchanged handler and mode reuse the grouped snapshot.

In the initial shared-summary implementation, each shared-layer query receives an independent summary map, lists, count wrappers and copied item stacks. The summary's exact total is copied through a small accessor, without comparing and merging already-grouped entries again; cached snapshots are never exposed to consumers. This matters because Create's arrival processing mutates the previous summary. Packagers retain their own early version-cache return, version recording and `submitNewArrivals` calls. Other inventory types, null targets and bottomless/packager special cases retain their upstream paths. The subsequent C3 development implementation changes when internal checks materialize a copy, as described below.

In the initial candidate, cache hits copy grouped entries instead of scanning every slot. The first query after another mutation still scans the full inventory and creates an independent copy, so gains depend on multiple packagers querying the same version; a lone packager does not gain a constant-time rescan. Comparator notification timing and dispatch, package extraction, order data and threshold-switch logic are unchanged by this step. Complete gameplay, arrivals, save/reload and independent performance acceptance for this second candidate remain pending.

Development compilation and Forge data-generation initialization passed with Create 6.0.6-150, 6.0.7-281 and 6.0.8-289. Exported packager bytecode confirms both hooks and retention of the original version-recording and arrival calls; generated resources were unchanged. The summary accessor's field and copy APIs were checked against all three Create class files. Data generation did not exercise summary copying or the live packaging/arrival pipeline.

## Incremental vault-summary rebuilding

The R2 development implementation keeps private per-slot contributions for each requested scan mode. Member callbacks mark slots dirty and advance the wrapper version immediately, including writes through a member's public inventory accessor. Normal combined-interface writes use the same underlying inventory operations and do not repeat the callback's version increment. Simulated or failed insertion/extraction does not mark slots; same-content slot assignments may conservatively advance the version.

The first request reads all slots. Later requests reread distinct dirty slots, identify their old and new Item buckets, and traverse the cached nonempty contributions in original slot order. Only affected buckets replay `InventorySummary.add`; other private buckets are reused. This retains NBT/capability-sensitive comparison and representative selection. The total is independently replayed in original order with Create's threshold-before-add integer rule. It is not computed by summing bucket totals. A changed package bucket can still require substantial comparisons when many different packages share one Item.

Candidate updates do not modify the existing contribution array or grouped entries before version/revision validation. Invalidated work is retried, including invalidation during outgoing stack copying. Requests allow at most three attempts; recursively requesting the same scan mode, or repeatedly mutating inventory during summary reads/copies, raises an explicit exception rather than publishing a half-updated result. Such callback behavior is outside the supported stable-read boundary and has not been exercised in gameplay.

NBT loading, member capacity changes, connectivity changes and capability invalidation retire the old wrapper and detach member tracking without controller/world lookups. Unattributed version or structure signals clear both modes for a full rebuild; an update touching every slot also uses full rebuilding. Invalidated wrappers do not retain new contribution caches. The implementation does not set an unmeasured partial-change density threshold.

Only requested modes allocate contributions. The controller checks for idle caches every 100 server ticks; a mode with no shared-layer request for five minutes of monotonic elapsed time releases its contribution and shared-summary cache. These are conservative housekeeping defaults, not measured optimal settings. Create-local cache hits do not touch this timer. The next shared-layer request cold-starts. Contributions are not saved to disk, do not add world-save fields or cache folders, and never replace the real per-block inventory. Releasing references permits garbage collection but does not guarantee an immediate decrease in process memory.

R2 retains the existing independent deep-copy boundary. R2 itself does not optimize copy frequency, arrival processing or repackager order-fragment search, and it does not change comparator batching. Private contributions can retain substantially more NBT/capability data than the grouped summaries alone; their retained memory has not been measured separately. Silent capability/NBT changes without slot notifications cannot be detected generally: unlike a full rescan after another slot changes, R2 may keep an unaffected bucket's old contribution. Such integrations need explicit notifications or conservative invalidation; universal compatibility is not claimed.

Both scan modes reached the shared layer in the reviewed reports. A later idle test recorded cache release on the same handler, followed by a 280-slot full rebuild and then a one-slot incremental rebuild. The reviewed reports record no rebuild/copy failures or discarded builds. This acceptance concerns R2 rebuilding, not a change to published 1.2.0 release status or approval of a copy optimization.

Scanning every slot for those same rebuild requests would require 3912710 and 8151860 reads, respectively: approximately 99.90% and 99.60% less read work. High-load rebuilding took 158.08 ms cumulatively; copying took 671.88 ms. In the overlapping JFR interval, 13 of 7234 server execution samples included incremental rebuilding. ## Deferred internal summary copies

The C3 development implementation allows Create's native `triggerStockCheck` path to retain a private grouped snapshot without immediately copying every representative stack. Single-use, owner-bound permits identify its direct forwarding calls; unrelated getter calls made by callbacks do not inherit permission. Deferral is limited to native ordinary packagers and repackagers using this mod's active combined vault handlers. Unknown subclasses and retired-handler reads make independent copies instead.

Public getters continue returning ordinary, independently mutable summaries. A public Create-local cache hit materializes a pending snapshot and replaces the machine's baseline with that same independent result. Subsequent local hits reuse it. Fresh public queries copy immediately. The native single machine cache and its scan-mode behavior are retained; C3 does not add separate input/extractable machine caches or expose lazy containers.

Native arrival processing still discovers its own promise queues. Only when it reaches the first difference traversal does C3 separate any private before/after summaries. Both sides must be independent: adding a missing negative group to the old summary can retain the new representative stack. An already independent old baseline, including one materialized by a callback, retains its identity so external references observe the native mutation. Original difference calculations and promise updates continue unchanged.

One three-attempt budget covers current-snapshot acquisition, necessary copies and validation before arrival side effects. Copying retains the mode's reentrancy guard. Failed or invalidated preparation clears the attempted version wait; it cannot make an uninstalled new summary appear cached. Once arrival mutation starts, the operation is not retried. Persistent invalidation and recursive copying raise explicit exceptions rather than exposing a private snapshot. These protections do not establish compatibility with arbitrary third-party callbacks or Mixins.

Saving `LastSummary` materializes the existing historical baseline when necessary, then uses the original format. It does not query current stock or submit new arrivals. Loading prunes only ownership markers that no longer match the native field. Pending state retains grouped data and value metadata, with a weak server identity for diagnostics; it does not retain the old wrapper, member arrays or contribution cache. Machine baselines can outlive shared-cache idle eviction, as independent machine summaries already could before C3.

C3 does not alter R2 grouping, item NBT/capability comparison, real inventories, order metadata, upgrades, comparator timing or repackager fragment search. It is a development change, not part of published 1.2.0 artifacts. Runtime acceptance and net performance benefit must be assessed separately from compilation and Mixin initialization.

Two existing isolated Create 6.0.8 GameTest selections passed against the C3 development sources: ten repackagers combined twenty fragments into ten packages containing 1280 items, and the partial-stack material case sent and unwrapped thirty packages containing 6720 items while preserving per-item quantities and the final network summary. Their schema-3 reports passed per-handler and aggregate identities with no build/copy failures or discarded results. The material window recorded 192 shared requests and 55 copies (24 fresh public queries, 31 public local-hit materializations); the repackager window recorded 210 shared requests and four save-triggered copies. These windows demonstrate deferred materialization, not a measured net speedup. Neither recorded arrival-difference copies or input-mode queries; promise-queue arrival semantics, arbitrary external mutations, dual-mode behavior, save/reload contents, exceptional callbacks and modpack load remain outside these checks. Current JFR copy/shared-read frames are `VaultSummarySnapshot.copy` and `VaultInventoryWrapper$SummaryRead.snapshot`; historical method-name filters need updating.

A subsequent source-based Create 6.0.8 contract suite passed eleven C3 cases in two independent JVMs, covering public container/NBT/capability isolation, native single-cache mode reuse, historical summary save/load, adjacent stock-link promise deduplication and difference handling, pre-effect copy failure recovery, bounded invalidation/recursion, idle release/capability replacement, recording-window protection and callback-materialized baseline identity. These use real vault members/wrappers and native packager methods with a controlled source binding; they do not establish physical connectivity, transport or arbitrary third-party compatibility.

Fixed-work comparisons against the exact pre-C3 R2 sources used 4000 slots, 20–200 native packages and ten packagers, in C3/R2/R2/C3 process order with ten warmup and thirty measured rounds per scene. Matching inventory/NBT fingerprints and slot-read work were verified. Internal-only checks avoided the baseline's 300 copies per measurement window; one public reader required 30; all public readers or saving every machine still required 300. Allocation fell substantially on deferred paths, but full-materialization controls showed timing regressions and unchanged local-cache hits incurred additional allocation and method overhead. Timings include diagnostics and only two JVMs per variant; these results support a conditional copy/allocation benefit, not uniform latency improvement or a modpack FPS/TPS claim. These measurements describe the first C3 implementation.

A follow-up development implementation creates full copy transactions only when the native path needs them. Ordinary local hits retain the original inventory/version check, while pending public reads and historical arrival baselines still enter the protected transaction. Invocation flags protect pending reads before the first capability callback and are restored after nested calls. Owner-bound immutable permits are reused, consumed before callbacks and cleared from the thread value on exit; an empty thread entry does not retain a machine. Copy events themselves form the transient diagnostic ledger, preserving discarded-copy and recording-window accounting without a per-query list. Public local-hit materialization reuses its observed handler and still checks source identity/version after copying. Independent stack copies, native arrival differences and historical save materialization remain unchanged.

The follow-up passed seventeen controlled-source native contracts on Create 6.0.6, 6.0.7 and 6.0.8, including invocation cleanup, early reentrancy protection, source replacement and native non-vault arrivals. A fresh four-JVM C3 comparison with fifty warmup and thirty measured rounds per scene reduced average per-JVM median unchanged-hit time by about 47% with diagnostics and 67% without; thread allocation fell about 72% and 81%, respectively. Full-materialization times did not improve uniformly: the 100/200-package all-public controls averaged about 4% higher, while all-save and actual queued-arrival controls were close to the first implementation. C3 still incurs more pure-hit overhead than R2. These are fixed-method source measurements, not installed-client or modpack performance acceptance.

The subsequent scoped NBT kernel keeps the actual native `ItemStack.copy()` call, capability serialization/construction and stack metadata handling. Only the ordinary tag-copy call for the authorized source stack uses direct traversal of standard `CompoundTag` and `ListTag` trees. Output maps, lists and mutable arrays remain independent; immutable value sharing and typed empty lists retain native behavior. Unknown tag subclasses use their virtual copy methods. Nested authorization and exceptions restore the prior thread value, and ordinary copies outside the scope continue through the original operation. Constructor invokers and explicit official/SRG call-site selectors are pinned to Minecraft 1.20.1; a missing tag-copy anchor leaves native copying in place. Mods that replace standard NBT copy behavior or modify the same call site need separate compatibility checks.

On 2026-10-17, the user ended further optimization and authorized a local checkpoint and an ordinary 1.2.0 build of R2, C3 and this NBT kernel. The recorded source checks, timing limitations and gameplay acceptance boundaries remain applicable; this decision does not add unperformed runtime checks or change the public release status.

Against frozen pre-kernel C3 sources, a four-JVM Create 6.0.8 comparison with fifty warmup and thirty measured rounds reduced average per-JVM median full-materialization time by about 13% for 100 package groups and 6% for 200 groups. The queued-arrival full round fell about 11%; thread allocation fell about 41–44% in these scenes. The twenty-package short-warmup control was about 30% slower, while a separate 500-warmup/100-sample comparison was about 27% faster. Unchanged-hit measurements also varied and were slower in the focused rerun, despite unchanged hit-path sources; this work does not establish a hit-path improvement or a uniform latency guarantee. Unscoped ordinary stack-copy controls retained the same steady-state allocation. These are controlled method measurements, not installed-client or modpack FPS/TPS acceptance, and do not eliminate capability initialization, native difference comparisons, summary grouping or serialization of already independent saved baselines.

## Full-package source scans

The development implementation stops further source-slot scans after an ordinary packager has filled all nine package slots with 64 items each. This shortcut is limited to complete, simple, single-link orders supplied by this mod's combined vault handler. Requested stacks must be ordinary vanilla items or block items with a maximum stack size of 64, no item tag, and Forge capabilities compatible with an absent capability dispatcher. Package items, bulky items, duplicate Item entries, crafting contexts, incomplete allocations and other inventory or packager implementations retain the upstream path. Compatibility with arbitrary nonserializing capability providers or third-party changes to vanilla stack behavior is not established by these checks.

Eligibility is checked against the original request queue inside `LogisticsManager.performPackageRequests`, before any context-carrying entry is removed. The decision is reused only for that queue during the same dispatch. A scoped thread-local connects the dispatch to the exact packager, queue and source handler; `finally` restores the previous scope for recursive calls and removes the outermost scope. Inserted-unit and full-package state use MixinExtras invocation-local values, so they reset for each package. No world-position cache, persistent data or test request sorting is introduced.

The hook changes only the source loop's effective bound after successful insertion and a check of all nine full slots. Create still performs the actual extraction, request subtraction, entry transitions, address/order checks, package numbering, final flags and context updates before reaching the next loop condition. Package creation, arrival accounting, animation, notifications and capability output remain upstream. Nine occupied slots or a single zero-transfer insertion do not activate the shortcut. Shared summaries, R2 rebuilding and independent summary copies are unchanged.

The `1.2.0-dev-packager-fullscan-1` production implementation passed isolated GameTest runs with Create 6.0.6-150, 6.0.7-281 and 6.0.8-289. Each version ran the previous six iron and ten mixed-inventory cases, plus two crafting-context fallback cases and one named-stack fallback case: 57 cases and 318 outputs in total, checked and drained through the packager capability. Source-call counts, per-item conservation, slot NBT, simple context and package metadata match the earlier isolated candidate for the original sixteen cases; crafting contexts and named stacks retain upstream scanning. An additional Create 6.0.8 run without input-order control passed the same nineteen cases and drained another 106 outputs, bringing the total to 76 cases and 424 outputs. The input-order control and call-site observer used for verification are local test tools and are excluded from runtime JARs. These checks do not establish packaged-client/modpack acceptance, full sustained-pipeline acceptance or net FPS/TPS improvement. Published 1.2.0 artifacts remain unchanged.

## Manual vault diagnostics

Development candidates provide operator-level commands (permission level 2):

```text
/create_bs diagnostics start
/create_bs diagnostics status
/create_bs diagnostics stop
```

Recording is disabled by default. `start` begins a fresh in-memory window without invalidating inventory caches or imposing a time limit. Another `start` retains the running window. `status` shows elapsed real time and aggregate counters; `stop` freezes the counters and writes a UTF-8 JSON report under `<game directory>/local/performance-diagnostics/create_bs/`. Server shutdown exports an active window automatically. A failed export leaves a frozen report available for another `stop` attempt and blocks a new window until export succeeds. Reports use unique filenames and do not overwrite earlier files or modify world saves.

Only server-thread operations on this mod's vault handlers are counted. The report includes elapsed wall time, server tick delta, versions, controller dimension/position, block type and slot count. Extractable and input-slot modes have separate counters. Per-handler details are bounded to 1024 entries; additional handlers contribute to an overflow aggregate included in the totals. Completed reports retain no world/server references. Details are sorted by rebuild time; they identify runtime handlers, so reconstructed capabilities receive distinct IDs.

| Field | Meaning |
|---|---|
| `query_calls` | Logical boolean-getter queries, including Create-local returns; forwarding does not count twice |
| `stock_check_queries`, `public_queries` | Logical query purposes identified by the direct-call permits |
| `query_attempts`, `query_incomplete_attempts` | Native-body attempts including retries, and attempts aborted before local/shared classification completes |
| `create_local_cache_hits` | Attempts satisfied by the packager's original version cache; a deferred result can still need materialization |
| `shared_requests`, `shared_cache_hits` | Queries reaching the shared wrapper and those reusing its snapshot |
| `getter_shared_requests`, `direct_api_shared_requests` | Shared requests from the native getter and direct independent-summary API |
| `build_attempts`, `retained_builds`, `discarded_builds`, `build_failures` | Scans completed/failed, and whether their result remained valid for caching |
| `completed_scanned_slots` | Slot visits in completed scans; aborted scans are excluded |
| `avoided_slot_visits` | Shared hits multiplied by the respective handler's slot count; an estimate of avoided scan work |
| `build_total_ms`, `build_max_ms`, `build_mean_ms` | Elapsed rebuild timing, including scheduling/GC rather than pure CPU time |
| `copy_calls`, `copy_failures`, `copy_total_ms`, `copy_max_ms` | Independent-summary copy count and elapsed timing |
| `copy_reason_calls` | Copy attempts split by public fresh/local queries, arrival before/after, saving, direct API and eager fallback |
| `copy_discarded`, `copied_groups` | Completed copies rejected before arrival effects, and groups copied in completed operations |
| `deferred_installs`, `deferred_materializations`, `deferred_drops` | Private baselines installed, converted to independent data or replaced without conversion |
| `version_increment_calls` | Wrapper version increments, not package count or all possible direct slot changes |
| `member_or_structure_clear_signals` | Additional invalidation notifications, potentially accompanying the same version increment |
| `member_slot_change_signals`, `idle_cache_releases` | R2 member callbacks and per-mode idle releases; callbacks are not distinct dirty-slot counts |
| `full_build_attempts`, `incremental_build_attempts` | R2 full and affected-bucket rebuild attempts; invalidated work can cause retries |
| `completed_dirty_slots`, `non_empty_contribution_visits` | Distinct dirty slots processed in completed attempts and nonempty contributions traversed in memory |
| `recomputed_item_buckets`, `recomputed_groups` | Item buckets affected and resulting groups rebuilt in completed attempts; removed buckets can produce zero groups |
| `incremental_avoided_slot_visits` | Unread slots in retained incremental builds, estimated against a full scan; separate from unchanged-summary hits |
| `packages_prepared` | Successful normal-packager preparation, including queued packages; repackager overrides are not covered in diagnostics1 |
| `packages_taken_via_capability` | Non-simulated package extraction through the packager inventory interface; hand pickups are excluded |
| `successful_unwrap_calls` | Successful normal-packager non-simulated unwrap calls, including accepted empty packages; repackager overrides are not covered in diagnostics1 |

Logical queries and native-body attempts are counted separately; a bounded retry is another attempt, not another logical query. Timing is only performed around whole rebuild/copy operations while recording; there is no per-slot timer or logging. Instrumentation hooks and ownership handling still have overhead while disabled. Reentrant timing can overlap, and hit rate/avoided slots do not alone measure a guaranteed speedup. Package counters measure flow within the window, not queue length; previously queued packages may leave during recording. They do not measure individual material quantities or prove inventory conservation. Use the report with a JFR from the same interval and comparable completed orders. Published 1.2.0 JARs do not include these commands.

R2 reports use schema version 2 and identify the summary strategy. `completed_scanned_slots` now counts actual inventory reads in completed full or incremental attempts; in-memory contribution visits are separate. Full and incremental attempts sum to `build_attempts`, but retries can make attempts exceed shared-layer cache misses. Unchanged-summary and retained-incremental avoided-slot estimates are separate and do not measure net time saved. Repackager preparation/receipt coverage remains unchanged.

C3 reports use schema version 3, retain R2 build counters and add `copy_strategy`. `query_calls` equals the two purpose counters; `shared_requests` equals its getter/direct API split; `copy_calls` equals the sum of copy reasons. For attempts with a stable vault source and no recording-boundary interruption, `query_attempts` equals local hits plus getter shared requests plus incomplete attempts. The schema-2 equalities between queries/local hits/shared requests and between copies/shared requests must not be applied to schema 3. Copies belong to the snapshot's origin handler/mode, which can differ from the current getter mode. Deferred baselines may cross recording windows, so installs need not balance materializations/drops within one window. Operations spanning stop/start do not update frozen counters; a later materialization is recorded in the window in which that copy starts and completes.

Development compilation, initialization and the packager query/preparation/unwrap hooks passed with Create 6.0.6-150, 6.0.7-281 and 6.0.8-289. The capability-extraction hook's two return sites and owner field were checked in all three versions' bytecode; that target was not loaded by data generation. ## Complete 3×3 end-layer regrouping

A complete end layer can fail ordinary connection search when its starting corner still belongs to an older 2×2 controller behind it. The additional connectivity step detects a full, same-type, same-axis 3×3 layer before ordinary formation and permits it to regroup independently.

It skips existing 3×3 structures, mismatched axes/types, source structures extending beyond the target cross-section, missing/unloaded members and active material-upgrade transactions. Existing connections are split through Create's API while keeping every member's inventory object and contents. The nine members form a width-3, length-1 structure; remaining members keep their inventories and queue ordinary regrouping.

Horizontal and vertical material vaults share the same geometry projection. This step does not alter vanilla Create vault connectivity. Independent-client feedback accepted the 1.1.1 repair; large-inventory regrouping and other combinations must not be inferred from that acceptance alone.

## Upgrade transactions

Player upgrades operate on stationary world structures. The transaction snapshots members and inventories, empties them silently, replaces the structure, restores inventory and charges components. Failure attempts rollback; failed recovery writes a recovery record. Preserve item NBT, per-member ownership, capacity checks and payment/rollback order when changing this path.
